`@sukujs/crypto` is a small set of security helpers built on the Web Crypto API. It has no
dependencies, runs on Node 22+, Bun and edge runtimes, and works with or without the rest of
Suku.

```bash
bun add @sukujs/crypto
```

<Callout type="warn">
  This package has not had an independent security audit. It implements no cryptography of
  its own: every operation is done by the platform, and the package adds safe defaults and
  input checking around it.
</Callout>

## Importing

Use the default export, which carries every function:

```ts
import sukuCrypto from '@sukujs/crypto';

const hash = await sukuCrypto.hashPassword(password);
const token = sukuCrypto.randomToken();
```

Each function is also a named export, which lets a bundler drop the ones you do not use:

```ts
import { hashPassword, randomToken } from '@sukujs/crypto';
```

They are the same functions. These pages use the default export.

## Choosing the right tool

Most mistakes come from using the wrong tool, not from using a tool badly.

| You need to | Use | Why |
| --- | --- | --- |
| Let a client prove who it is on each request | [JWT](/docs/crypto/jwt) | Checked without a database lookup. |
| Let other services check your tokens | [JWT](/docs/crypto/jwt) with a key pair | They hold only the public key, so they cannot make tokens. |
| Store a password | [`hashPassword`](/docs/crypto/passwords) | Slow on purpose, so stolen hashes are hard to crack. |
| Give a client a value it may read but not change | [`createSigner`](/docs/crypto/signed-and-sealed) | Any change is detected. |
| Give a client a value it must not read | [`createSealer`](/docs/crypto/signed-and-sealed) | Encrypted, change-proof, and can expire. |
| Store data nobody else can read, such as a field or a file | [`createEncrypter`](/docs/crypto/encryption) | A copied database shows only ciphertext. |
| Let one app encrypt what only another app can read | [`createEncrypter`](/docs/crypto/encryption#encrypt-with-a-public-key) with `RSA-OAEP-256` | The app that encrypts cannot decrypt. |
| Create a session id, API key or reset token | `randomToken()` | 256 random bits, impossible to guess. |
| Fingerprint a file or make a cache key | `sha256()` | Fast. Never use it for passwords. |
| Compare two secrets | `timingSafeEqual()` | Takes the same time wherever they differ, so it leaks nothing. |

### Signed, sealed, or a JWT?

| | Signed value | Sealed value | JWT |
| --- | --- | --- | --- |
| Client can read it | Yes | No | Yes |
| Client can change it | No | No | No |
| Built-in expiry | No | Optional `ttl` | Yes, by default |
| Verifiable by another service | Only with the shared secret | Only with the shared secret | Yes, with a public key |
| Typical use | Cookie value, webhook, link | Encrypted cookie, OAuth state, reset link | API authentication |

A JWT's payload is only encoded, not encrypted. Anyone holding the token can read it.

## Secrets

Every helper that takes a secret requires at least 32 bytes and refuses anything shorter.
Generate one per purpose and keep it in your environment.

```ts
import sukuCrypto from '@sukujs/crypto';

console.log(sukuCrypto.randomToken(32));   // run once, paste into your secret store
```

Validate them at startup with [configuration](/docs/configuration), so a missing secret stops
the app before it serves a request.

```ts
export const Env = defineConfig(
  'env',
  z.object({
    JWT_SECRET: z.string().min(43),
    COOKIE_SECRET: z.string().min(43),
  }),
);
```

## Errors

What happens when a check fails depends on whose fault it usually is.

| Function | On failure | Usually because | Answer the client with |
| --- | --- | --- | --- |
| `verifyPassword` | returns `false` | a wrong password | `401` |
| `signer.unpack`, `sealer.unseal` | returns `undefined` | a stale or edited cookie or link | `401`, or treat it as missing |
| `jwt.verify` | throws `JwtError` | an expired or forged token | `401` |
| `encrypter.decrypt` | throws `CryptoError` | a wrong key or damaged stored data: your side | `500`, and log it |

Every error has a `code`, such as `expired` or `decryption_failed`, for your logs. Do not send
it to the client: telling an attacker why a token failed helps them. See
[best practices](/docs/crypto/best-practices#do-not-explain-failures-to-the-client).

## Not included

Encrypted JWTs (JWE), fetching keys from an identity provider (JWKS), OAuth and OpenID
Connect flows, token revocation lists, Argon2 or bcrypt, streaming encryption of large files,
and encryption with a password.
